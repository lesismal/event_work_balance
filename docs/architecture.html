ep Single-loop epoll
architecture / implementation-aligned
Concurrency architecture · Linux · ET

一个 I/O 核心，
逐连接串行。

单个 epoll event loop 管理所有 fd 和 I/O 关注；每个 connection 用自己的 FIFO 保存事件顺序；线程池动态选择空闲 worker，一次排空该 connection 的全部事件。

核心不变量 调度单位是 connection，不是单个事件。connection 与 worker 没有固定绑定；但同一时刻，一个 connection 最多只有一个 worker 执行。

Why no affinity?

让任务追随空闲算力，而不是固守连接归属

无连接亲和性不是偶然结果，而是为了解决“连接分配完成后，实际负载仍持续变化”的动态不均衡。

Fixed ownership · classic multi-worker

fd 长期归属某个 worker

类似经典 Nginx 多 worker 进程模型：每个 worker 有自己的事件循环和连接集合。即使接入阶段尽量均分，后续负载仍可能倾斜。

VS
Dynamic dispatch · this architecture

connection 每轮由空闲 worker 领取

所有可执行 connection 进入共享 ready queue。线程池把下一份连接任务交给当时空闲的 worker，调度依据是实时可用算力，而不是历史 fd 归属。

worker #072%
worker #168%
worker #271%
connection 是可迁移的调度单位，不固定绑定线程
空闲 worker 主动消费 ready queue，吸收任务量波动
每轮仍由单 worker 排空 FIFO，动态均衡不破坏顺序
平衡的对象是“待执行任务量”，而不只是 fd 数量。动态 worker 选择提升线程池利用率；connection 自身队列继续承担顺序与并发隔离。

背景参考：Nginx 官方资料说明其采用多个 worker 进程，每个 worker 具有事件处理能力和连接容量；具体接入分配还会受到 accept_mutex、EPOLLEXCLUSIVE 或 reuseport 等机制影响。参见 Development guide 与 Core functionality。

并发设计的三条边界

这三条规则共同把“一个全局 I/O 循环”和“多个业务执行线程”组合成可推理的系统。

RULE / 01

fd 控制权属于 event loop

worker 不直接修改 epoll 注册或最终 close；它只通过 command queue 表达意图，减少 fd 重用与生命周期竞争。

epoll_ctlacceptclose
RULE / 02

顺序属于 connection

事件先进入逐 connection FIFO；scheduled 为 true 的整个期间不会再次投递。领取它的 worker 连续排空队列，因此同一连接不会有两个线程并发执行，也不会乱序。

mutexFIFOscheduledsingle executor
RULE / 03

线程没有连接亲和性

connection 不固定绑定某个 worker，用共享 ready queue 避免 fd 数量或任务量分布不均造成的 worker 负载倾斜。本轮可能由 worker #2 执行，下轮可能由 worker #0 执行；顺序保证来自连接队列与状态锁，而非线程绑定。
